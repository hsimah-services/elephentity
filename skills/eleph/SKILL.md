# Using Elephentity

Elephentity compiles YAML specs into locked source code, in PHP or C#. Everything
mechanical — entities, mutators, finders, enums, hydrators, storage manifests, GraphQL
registration — is generated. You write only the parts no generator could infer, and
those arrive as interfaces the generator emits for you.

`eleph` is one Rust binary that reads the specs. It writes no code itself: each
**target** in `eleph.json` names a **builder** (a separate program) that emits one kind
of output. That is why the same spec produces PHP or C#.

## The one rule

**Never edit a file with a `GENERATED BY Elephentity` header.** Its digest is checked by the
build, so an edit fails CI rather than surviving. If the generated code is wrong,
the spec is wrong: change the spec and regenerate. If the spec cannot say what you
need, see "What Elephentity cannot express" and tell the person rather than patching
the output.

This is the framework's whole premise. A codebase where the same idea is expressed the
same way in every entity is navigable; one where each entity was hand-written is not.

## Orient yourself first

Before changing anything, find out which stack you are on:

```bash
cat eleph.json                 # targets → builders → which language and storage
cat spec/project.yml           # storage.driver: memory | sqlite | cosmos, tablePrefix
ls spec/entities spec/types spec/patterns
eleph --version
```

| `eleph.json` builder | Stack | Hand-written code is |
|---|---|---|
| `eleph-gen-php`, `-memory`, `-graphql-php` | PHP (Composer packages `elephentity/*`) | `src/`, built by your container |
| `eleph-gen-csharp`, `-cosmos`, `-graphql-csharp` | C# (NuGet `Elephentity.*`) | your project, registered with DI |
| `eleph-gen-sqlite`, `eleph-gen-tsquid` | either stack: the target's `language` is `"php"` or `"csharp"` (required, no default; `csharp` also needs a `namespace`) | none |

A builder written `name@version` is pinned and fetched by `eleph install`; a path such as
`vendor/bin/eleph-gen-php` was installed by Composer. If `eleph` is not on the `PATH`:

```bash
curl -fsSL https://github.com/hsimah-services/elephentity/releases/latest/download/install.sh | sh
```

(`install.ps1` on Windows.) It needs no PHP, even for a PHP project.

## Project layout

```
eleph.json          spec directory and one entry per target
spec/
  project.yml       the storage driver and table prefix — required
  entities/*.yml    one file per entity
  patterns/*.yml    reusable fragments an entity pulls in with `use:`
  types/*.yml       declared value types and enums
src/                your code — handlers, verifiers, value classes
generated/          machine-owned, committed, never edited
```

`eleph.json` — every target needs a `builder`, because Elephentity generates nothing
itself. PHP:

```json
{
    "spec": "spec",
    "targets": {
        "php": {
            "builder": "vendor/bin/eleph-gen-php",
            "output": "generated",
            "namespace": "App\\Entity",
            "typeNamespace": "App\\Type"
        },
        "memory": { "builder": "vendor/bin/eleph-gen-memory", "output": "generated/memory" }
    }
}
```

C#:

```json
{
    "spec": "spec",
    "codegen": "eleph-codegen@0.7.0",
    "targets": {
        "csharp": {
            "builder": "eleph-gen-csharp@0.1.0-alpha.1",
            "output": "Generated",
            "namespace": "App.Entity",
            "typeNamespace": "App.Type",
            "check": ["dotnet", "test", "tests/Contracts"]
        }
    }
}
```

The versions above are examples; keep whatever the project pins. A driver or integration
the spec asks for must have a target that provides it: `driver: sqlite` with no sqlite
target, or `integrations: { graphql: … }` with no graphql target, is a `validate` error.
`eleph-codegen doctor` (PHP projects) confirms the builders are where the config expects.

## The loop

```bash
eleph install      # only if eleph.json pins "name@version" programs
eleph fmt          # canonical key order (reports; you fix by hand)
eleph validate     # well-formed and semantically closed
eleph generate     # write the tree
#   ... implement anything new under the Contract/ folders ...
eleph check        # each target's own coherence check
```

PHP projects then also run `vendor/bin/phpstan analyse` and `vendor/bin/phpunit`; C#
projects run `dotnet build` and `dotnet test`. Run them in that order. `check` inspects
the generated code on disk, so it must follow `generate`.

In CI, `generate --check` replaces `generate`: it regenerates in memory and fails if
the committed tree differs. See `reference/commands.md` for what each gate catches and
how to read its output. The output of every gate is meant for you: it names the file,
the path inside it and a stable code, and one run reports every problem. Fix them all,
then re-run.

If a command is not installed or a builder cannot be found, say so and stop. Do not
hand-write what a missing builder would have generated.

## Working out what you have to write

After `generate`, this is mechanical. PHP:

```bash
ls generated/*/Contract/    # interfaces you must implement
```

C# puts them in the `{namespace}.Contract` namespace (`I<Entity><Name>Query`,
`…Action`, `…SideEffect`, `…Verifier`, `…ReadPolicy`, `…WritePolicy`), and the generated
`Catalogue.Contracts()` lists them.

Every one is an interface with no implementation. In PHP **the application will not boot
until one exists** (`MissingImplementations` names all of them at once). In C#, `eleph
check` and `ContractCheck` name what is unregistered. There is no other way to find out —
that is the design.

Two more categories the contracts folder does not cover:

- **Value classes.** A type declared with `processors: true` names a class the generator
  never emits (`App\Type\Money`, or `Money` in `typeNamespace`), because a value object
  has behaviour no generator can invent. You write it.
- **Wiring.** Generated classes are assembled by your container: a PSR-11 container in
  PHP, `Add<Project>Entities(this IServiceCollection)` in C#.

`reference/bespoke-files.md` covers each kind, with what a correct implementation looks
like, and where a working application to copy the wiring from lives.

## Changing something

| You want | Change |
|---|---|
| a new field | `fields:` on the entity |
| a field to stop being settable | `immutable: true` — the setter disappears |
| a relationship | `edges:` — see the cardinality table in `reference/spec-format.md` |
| a query | `queries:` — you get a finder method and an interface to implement |
| a named write operation | `actions:` — declare what it `writes:`, and it can touch nothing else |
| something to happen on commit | `sideEffects:` — pick `preCommit` or `postCommit` deliberately |
| a rule spanning two fields | `verify: true` on a field — the verifier sees the whole pending state |
| the same fields on many entities | a pattern, pulled in with `use:` (see `patterns/` in the framework repository for the catalogue) |
| a rule about who may read or write | `readPolicies:` / `writePolicies:` — see `reference/spec-format.md` |

Specs carry no application namespaces: `handler: true`, `verify: true` and
`processors: true` mean "generate the interface", and the names come from `eleph.json`.
Do not add `id` to an entity (it is implicit), and do not name columns, tables beyond
`storage.table`, or join tables — placement is inferred.

## What Elephentity cannot express

Say so plainly rather than working around it:

- **Lists of scalars.** No `list` modifier. Use `json` (not indexable) or model the
  values as a child entity (indexable, changes the model).
- **Composite value objects.** A declared type aliases exactly one primitive, so a
  two-field value object has to be two fields.
- **Field-level visibility.** Read and write policies decide whether an entity may be
  read or changed by a given viewer; there is no per-field rule. Exposing an entity
  exposes every field on it.
- **Rows outside the entity's own table.** Nothing creates or maintains a row elsewhere
  for an entity. An application that wants one writes it in a `postCommit` sideEffect.
- **Dropped platforms.** WordPress and WPGraphQL are not supported; do not add
  `driver: wordpress`, a post-type `handle` or the `wpgraphql` integration.
