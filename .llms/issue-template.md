# Issue template

Title: what changed, then what this repository has to do about it. Both halves — a title
that only says what changed makes the reader open the issue to find out if it is theirs.

> `Envelope::IR_VERSION` is now 1.1 — bump to match, or builds refuse

Body:

```markdown
## What changed

<commit subject> — hsimah/<source repo>@<sha>

<The specific thing. A constant and its old and new value, a JSON key added or
renamed, a change to generated bytes. One or two sentences of why, because the
"what" alone does not tell the reader whether their situation is covered.>

## What this repository needs

- [ ] <Concrete change, naming the file.>
- [ ] <Second one, if there is one.>

## Verifying

```bash
<command>
```

<What passing looks like. If it is "the golden fixtures move", say which ones and
that the diff is expected.>

## Ordering

<One of:>
- These must merge together — the version gate refuses in both directions, so any
  other order is a window where every build fails.
- This repository can follow at its own pace; the current release keeps working
  until it does.

Filed from hsimah/<source repo>@<sha>. Contract: `.llms/cross-repo.md`.
```

## Notes

- **Do not paste the diff.** Link the commit. The diff is the change in the source
  repository's vocabulary; the issue's job is to translate it into this one's.
- **Say what happens if it is ignored**, when the answer is worse than "nothing yet".
  "Builds refuse" and "generated code silently loses the field" want different urgency
  and the reader cannot infer which from a checklist.
- **One issue per repository**, cross-linked, not one issue mentioning three. Each is a
  different piece of work with a different owner and a different definition of done.
